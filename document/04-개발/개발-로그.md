### ERD 1차 검토 라운드 — 게시판/댓글/쿠폰/배송추적/공통코드 추가
`document/03-설계/ERD.md`의 "검토 필요 사항" 중 일부를 이번 라운드에서 결정하고 `schema.sql`에 반영. 자세한 근거는 `ERD.md`의 "이번 라운드 설계 결정" 절 참고, 요약은 아래.

- **게시판/게시물** — `board_posts`(통합 게시물) + `common_codes`(게시판 종류) 신설. 이벤트는 별도 테이블이 아니라 `common_codes`에서 NOTICE 코드의 하위(parent_id)로 등록. 조회수/좋아요/싫어요 컬럼 추가. 리뷰는 주문/평점에 강하게 묶여 있어 게시물과 통합하지 않고 별도 유지하되, 카운터 컬럼 구조와 댓글 연결 방식은 동일하게 맞춤.
- **댓글 통합** — `comments` 테이블 하나로 게시물/리뷰 댓글을 모두 처리. `post_id`/`review_id` 중 정확히 하나만 채워지도록 `CHECK (num_nonnulls(...) = 1)`로 강제(배타적 FK) — files에서 지양한 문자열 기반 폴리모픽 대신 실제 FK 무결성을 유지하면서 통합. `parent_id` 자기참조로 대댓글 지원, 좋아요/싫어요 컬럼 포함.
- **쿠폰/할인** — `coupons`(정의) + `account_coupons`(계정별 보유/사용) 2테이블. `issue_type`(SHARED_CODE 공용코드 / TARGETED 개별발급) 컬럼으로 두 방식을 한 구조로 처리, `UNIQUE(coupon_id, account_id)`로 "계정당 1회"를 두 방식 모두에서 자동 보장. `orders.discount_amount` 컬럼 추가(적용 할인액 스냅샷).
- **배송 상태 추적** — `deliveries`(주문당 1건, 현재 상태) + `delivery_status_histories`(상태 변경 이력) 분리 신설. orders.status(주문 생애주기)와 역할 분리.
- **재고 이력** — 이번엔 보류. 기존 테이블 변경 없이 순수 추가만 하면 되는 구조라 나중에 추가해도 비용 차이가 거의 없다고 판단.

### ERD 2차 검토 라운드 — PK 채번 규칙, 공통코드 전면 적용, 연락처 정규화
1차 라운드 직후 이어진 피드백을 반영. 자세한 근거는 `ERD.md`의 "2차 라운드 설계 결정" 절, 컬럼별 매핑은 "공통 코드 규칙" 표 참고. `schema.sql` 전체를 이 규칙에 맞춰 다시 작성함.

- **PK 채번 규칙** — 모든 PK를 `BIGSERIAL`에서 `VARCHAR(17)`("4자리 대문자 테이블코드 + 13자리 시퀀스 숫자")로 전환. 숫자는 `SEQ_<테이블명>_01` 시퀀스를 `NEXTVAL`로 채번 후 `LPAD`로 0-padding. `files.id`만 예외로 UUID 유지 — 공개 URL에 그대로 쓰이는 PK라 코드+순번 조합을 쓰면 오히려 추측이 쉬워져 기존 IDOR 방지 규칙과 충돌하기 때문. 이 내부 PK는 절대 URL에 노출하지 않는다는 점을 문서에 명시.
- **공통 코드 전면 적용** — `department`, `admin_level`, `approval_status`, `grade`, `account_type`, `status`, `method`, `issue_type`, `discount_type` 등 분류/상태성 컬럼을 모두 `common_codes` 참조 `*_code_id`로 전환(예: `department` → `department_code_id`). 새로 생긴 게시판/쿠폰/배송 관련 컬럼도 처음부터 이 방식으로 설계해 일관성 확보.
- **연락처 정규화** — 전화번호는 `accounts.phone_1`/`phone_2`/`phone_3` 3개 컬럼으로 확장(별도 테이블로 정규화하지 않음 — 개수가 적고 고정적이라 판단). 이메일은 `account_emails` 테이블로 정규화하고 `is_primary` + 부분 유니크 인덱스(`WHERE is_primary`)로 계정당 대표 이메일이 최대 1개로 유지되도록 실제 제약을 걸었다.
- 새로 생긴 미결 항목: 이메일 정규화 이후 로그인 인증을 어떤 이메일 기준으로 할지, `common_codes` 초기 시드 데이터 확정 — `ERD.md` 검토 필요 사항에 기록.
- 다음 단계: `common_codes` 시드값 확정, 남은 미결 항목 논의 후 IntelliJ DDL Data Source로 전체 재시각화

### ERD 3차 검토 라운드 — 공통 코드 값(code) 채번 방식 정정
- **공통 코드 값 비식별화** — `common_codes.code`에 `'ADMIN'`, `'ACTIVE'`처럼 의미가 읽히는 문자열을 쓰는 것으로 처음 설계했으나, 잘못 이해한 부분이라 정정. PK와 동일한 사상으로, `code_group`별 4~5자리 대문자 접두어 + 4자리 숫자(그룹마다 0001부터 개별 채번)로 값 자체는 무엇인지 알 수 없게 바꿈(예: `DEPR0001`). 실제 의미는 `code_name`에만 담고, 애플리케이션 로직도 `code` 문자열 비교 대신 FK인 `*_code_id`로만 참조. `ERD.md` "공통 코드 규칙", `schema.sql` 하단 시드 예시 갱신.

### ERD 4차 검토 라운드 — 자료형 이식성, description 컬럼, code_group/parent_id 역할 정리
- **자료형 이식성** — `BOOLEAN`/`TIMESTAMPTZ`처럼 Postgres 전용 색이 짙은 자료형을 프로젝트 전체에서 제거. `BOOLEAN`은 `CHAR(1)` `'Y'/'N'` + `CHECK`로, 컬럼명도 `del_yn` 관례에 맞춰 `*_yn`으로 통일(`is_default`→`default_yn`, `is_active`→`active_yn`, `is_primary`→`primary_yn`). `TIMESTAMPTZ`는 전부 `TIMESTAMP`로 교체. `UUID`는 보안 규칙(추측 불가능한 공개 식별자)과 직결돼 있어 예외로 유지 — 바꾸면 목적 자체가 무너지기 때문.
- **`common_codes.description` 추가** — `code`가 `ACTP0001`처럼 비식별화되면서, 짧은 라벨(`code_name`) 외에 더 상세한 설명을 남길 곳이 필요해져 nullable `description` 컬럼 추가.
- **`code_group` vs `parent_id`** — "겹치는 역할 아니냐"는 지적에 답: 각각 "분류"와 "분류 내 계층"이라는 다른 질문에 답하므로 실제로는 겹치지 않음. 대안(그룹을 루트 노드로 흡수)도 검토했지만 흔한 조회가 재귀 쿼리가 되는 단점이 있어 현 구조 유지, 대신 자식 코드의 `code_group`이 부모와 같아야 한다는 비정규화 규칙을 명문화.
- `schema.sql`의 `code` 컬럼 인라인 주석에 예전 예시(`NOTICE, ACTIVE`)가 그대로 남아있던 것도 발견해 새 규칙에 맞게 수정.
- 다음 단계: (변경 없음) `common_codes` 시드값 확정, 남은 미결 항목 논의 후 IntelliJ DDL Data Source로 재시각화

### ERD 6차 라운드 — 남은 사항 처리 (수수료율 초안, 관리자 권한 확정, 옵션 상태 세분화)

### ERD 7차 라운드 — 알림 기능 추가, 공통코드 예비컬럼 제안 검토, 설계 원칙 재확인
- **알림 기능** — `notifications`(인앱 피드) + `notification_settings`(계정별 유형 on/off) 신설. 요청받은 3종(공지/이벤트당첨/배송완료) 외에 주문접수·결제완료/배송시작/취소환불완료/쿠폰발급·만료임박/재입고/리뷰작성요청/댓글·대댓글/판매자승인결과/정산완료/문의답변등록까지 총 14종으로 확장. 알림이 가리키는 원본은 `target_type_code_id`(공통코드 FK) + `target_id`(실제 FK 없음)로 느슨하게 참조 — `files`/`comments`에서 지양한 폴리모픽을 이번엔 의도적 예외로 채택(대상 종류가 계속 늘고, 원본 삭제돼도 알림 로그는 남아도 무방해 무결성 강제가 덜 중요하다고 판단). 자세한 근거는 `ERD.md` "7차 라운드 설계 결정" 참고.
- **공통코드 예비 속성(attr_1~5) 제안 — 비채택** — 코드마다 다른 부가데이터를 담기 위한 범용 예비 컬럼 제안을 검토했으나 EAV 안티패턴(타입 안전성 상실, 컬럼 의미가 code_group마다 달라짐, 5개라는 임의적 개수 한계)을 이유로 권장하지 않음. `seller_grade_policies`처럼 필요한 그룹에만 타입이 명확한 확장 테이블을 두는 기존 패턴 유지가 낫다고 판단해 그렇게 설명하고 사용자 확인받음.
- **설계 경계 재확인** — "앱 로직(권한-화면 매핑, 알림 발송, 수수료 계산 실행, 자동 상태전환 등)은 ERD가 아니라 프론트/백엔드에서"라는 방향에 동의. ERD는 데이터 구조 + DB가 직접 지킬 수 있는 제약(UNIQUE/CHECK/FK)까지만 책임지는 경계를 재확인.
- **공통코드 관리 화면 별도 제작 예정** — SQL 직접 수정 대신 전용 관리자 페이지에서 조정하기로 확인. attr_1~5 비채택 판단과 같은 방향(관리 화면이 있다면 필드별 명확한 타입이 더 유리).

### ERD 9차 라운드 — 계정/회사 구조 근본 개편 + 대량등록(엑셀) 스테이징
사용자가 "계정은 관리자/일반 두 종류로만 나누고, 판매자는 일반계정이 가질 수 있는 자격으로, 그 상위 개념으로 회사(그룹)를 두면 어떨지" 제안. 여러 라운드에 걸쳐 세부사항(직책/권한 회사별 관리, 1인 다회사 지원, 대표자 변경을 번거롭게)을 확정받은 뒤, 여기에 더해 상품/송장/재고 대량등록(엑셀) 기능까지 한 번에 반영. `schema.sql` 전체를 이 구조에 맞춰 처음부터 다시 작성함(54개 테이블).

- **계정 2분할** — `ACCOUNT_TYPE`을 ADMIN/SELLER/BUYER 3종 → ADMIN/GENERAL 2종으로 축소. `buyers` → `general_accounts`로 개명(구매 기본 프로필이라는 의미 명확화).
- **회사(companies) 신설** — 기존 `sellers`(accounts 1:1)를 폐기하고, accounts와 종속되지 않는 `companies` 신설. `company_members`(계정-회사-직책 다대다)로 1회사 다직원, 1인 다회사를 모두 지원 — 후자는 다대다 구조 자체에서 자연히 따라오는 결과라 추가 설계 불필요했음.
- **회사별 직책/권한** — `company_roles`(직책 이름은 회사 자유), `company_role_permissions`(권한 "종류"는 `COMPANY_PERMISSION` 공통코드로 시스템 고정, 직책이 그 권한들을 묶는 역할).
- **대표자 컬럼 + 변경 절차** — `companies.owner_account_id`로 대표자 명시. 직접 UPDATE 대신 `company_owner_change_requests`(접수→검토중→승인/반려) 절차를 거치도록 의도적으로 번거롭게 설계 — 사업자 명의 변경은 분쟁 소지가 있어 사유/이력을 남기는 게 낫다고 판단.
- **연쇄 리네임** — `seller_id`를 쓰던 모든 컬럼(products/deliveries/settlements/coupon_targets)이 `company_id`로, `SELLER_GRADE`/`SELLER_APPROVAL_STATUS`/`BUYER_GRADE` 공통코드 그룹도 `COMPANY_GRADE`/`COMPANY_APPROVAL_STATUS`/`GENERAL_GRADE`로 개명.
- **대량등록(엑셀) 스테이징** — 상품등록/송장번호등록/재고·가격변경 3종 우선 구현(카테고리 일괄등록·직원 일괄초대는 제외 확정). `temp_bulk_import_batches`(배치 헤더, 3종 공용) + 종류별 `temp_product_import_rows`/`temp_tracking_import_rows`/`temp_stock_import_rows`(엑셀 원본, 검증 전 문자열 보관). 배치 헤더만 공용으로 둔 이유는 종류마다 필요한 컬럼이 완전히 달라 한 테이블에 억지로 담으면 `attr_1~5`를 거부했던 것과 같은 EAV 문제가 재발하기 때문.
- **`temp_` 접두어 컨벤션** — 스테이징 테이블임을 이름으로 표시. 취소 시 상세 행은 실제 DELETE(소프트 삭제 관행의 명시적 예외), 배치 헤더는 상태만 '취소됨'/'만료됨'으로 바꿔 가볍게 남김. 방치된 배치 정리는 스케줄러(백엔드) 몫, 스키마는 상태값 + `ON DELETE CASCADE`까지만 준비.
- 테이블 수 46 → **54개**(시퀀스 51개)로 증가. 전체 파일 재작성 후 재검증 완료(괄호 균형, 시퀀스 선언/사용 일치, 54개 테이블 선언 순서 의존성, 구 sellers/buyers 참조 잔존 여부 — 전부 문제없음).
- 다음 단계: 남은 항목은 운영 정책 수치(수수료율/배송비/적립률/클레임 SLA/COMPANY_PERMISSION 목록/엑셀 템플릿 양식 등)뿐 — IntelliJ DDL Data Source 재시각화 → 확정되면 VM Postgres 적용

### 백엔드 1차 구현 + 프론트(앱) 초기 구현 + git 정리
DB 설계 이후 실제 구현으로 전환. 요약:

- **백엔드**: Spring Boot 4.1 + Java 21. 전역 예외처리(RFC 7807), 로컬 파일 저장, JWT 로그인/회원가입, 상품 목록·상세 조회 API(정렬/페이지네이션), Flyway로 `schema.sql`을 `V1` 마이그레이션화 + 관리자 테스트 계정과 더미 상품 10개를 `V2` 시드로 추가. PK 채번은 커스텀 제너레이터 대신 `GenerationType.IDENTITY`로 결정(Postgres `DEFAULT` 식이 그대로 동작).
- **모바일**: Expo(React Native) + TypeScript. A안(미니멀 모노크롬) 디자인이 "무신사 카피"라는 피드백을 받아 의류 테크팩(생산 스펙시트) 표기를 모티프로 한 독자적 방향으로 전면 재설계. 디자인 토큰 + 재사용 컴포넌트(Button/TextField/Tag/ProductCard/OrderSummary/Table/SortBar) + 스타일가이드 화면 구축, 이후 홈 화면을 실제 백엔드 API(TanStack Query)에 연동해 실시간 상품 목록/정렬까지 동작 확인.
- **트러블슈팅**: npm의 Windows `.cmd` 래퍼 버그로 `create-expo-app` 실패(템플릿 직접 추출로 우회), 이 머신에 JDK가 아예 없어 프로젝트 스코프로 해결, Spring Boot 4의 autoconfigure 모듈 분리로 Flyway가 기본 동작 안 함(전용 스타터 추가로 해결), Hibernate가 Postgres `CHAR(1)`을 `VARCHAR`로 오인(`@JdbcTypeCode` 추가), 상대경로 저장소 위치가 실행 방식(터미널 vs IntelliJ)에 따라 다른 작업 디렉터리를 가리켜 이미지 서빙이 500 나던 버그(Spring `ApplicationHome` 기반으로 `build/` 랜드마크를 찾아 모듈 루트를 역산하도록 수정, 잘못된 cwd에서 재현 후 확인).
- **git 정리**: 그동안 미커밋 상태였던 `mobile/`, `document/`를 포함해 전체 커밋. VM 안의 별도 저장소로 있던 인프라(Docker Compose: Postgres+Jenkins)를 이 저장소의 `infra/`로 통합. 머신 종속적이던 `backend/gradle.properties`(하드코딩된 JDK 경로) 제거. 새 머신에서 VirtualBox+Ubuntu만으로 전체 환경을 재현하는 절차를 `document/06-배포운영/개발환경-세팅.md`로 문서화, 루트에 `README.md` 신설.

### 로그인/회원가입 화면 + 상품 상세 화면 + 세션 유지
주말 공백 후 재개. "지난번 계획대로" 로그인/회원가입 화면 → 상품 상세 순으로 진행, DTO/빌더 패턴은 기존 방식(레코드 + `@Builder`/`@SuperBuilder`) 그대로 유지.

- **백엔드**: `GET /api/auth/me` 추가(JWT 인증 필터를 실제로 거치는 첫 엔드포인트) — 앱이 저장된 토큰으로 로그인 세션을 복원할 때 씀. `SecurityConfig`의 공개 경로를 `/api/auth/**`(전체)에서 `/login`·`/signup`만으로 좁힘.
- **모바일**: 계정 탭(로그인 폼 ↔ 로그인 시 프로필+로그아웃), 회원가입 화면, 상품 상세 화면(`GET /api/products/{uuid}`), 홈 화면 상품 카드 탭 → 상세 이동. 인증 상태는 zustand + 토큰 영속화(네이티브는 SecureStore, 웹은 localStorage).
- **구조 변경(버그 수정)**: `NativeTabs`를 루트 내비게이터로 그대로 쓰고 있었더니 tab으로 선언 안 된 라우트(상품 상세, 회원가입)로 이동해도 그냥 홈으로 남아있는 문제 발견 — `(tabs)` 라우트 그룹 + 루트 `Stack`으로 재구성해서 해결(탭 화면은 `(tabs)/`로 이동, 상세/회원가입은 스택 위에 push).
- **트러블슈팅**: `expo-secure-store`가 웹에서는 실제 저장 함수가 구현 안 돼 있어 조용히 실패(웹은 localStorage로 분기 처리). `/me`를 코드에 추가하고도 백엔드를 재시작 안 해서 한참 "500 No static resource" 헤맴(재시작 후 정상). Zustand 스토어가 Fast Refresh로 안 갈리는 경우가 있어 코드 수정 후에는 dev 서버 자체를 재시작해서 검증.

### 장바구니 기능 + 소프트 삭제/UNIQUE 충돌 일괄 수정
- **백엔드**: `carts`/`cart_items` 엔티티·레포지토리, 장바구니 API 4종(`GET /api/cart`, `POST /api/cart/items`, `PATCH /api/cart/items/{id}`, `DELETE /api/cart/items/{id}`) 추가. 전부 인증 필수. DTO는 기존과 동일하게 record + `@Builder`, 엔티티는 `@SuperBuilder`.
  - 장바구니는 "지금 시점의 상품 정보"를 보여줘야 하는 라이브 데이터라 담을 때 가격을 스냅샷하지 않고 조회 시 `products`를 조인해 현재 가격/재고를 가져온다(스냅샷은 주문 확정 시 `order_items`에서). 13차 라운드에서 "carts/wishlists는 스냅샷 대상 아님"으로 정리한 것과 일치.
  - `carts.account_id`가 `general_accounts`를 참조해 관리자 계정은 장바구니를 못 가진다 → FK 위반 500 대신 `NOT_A_SHOPPER`(403)로 명확히 막음. 재고 초과는 `OUT_OF_STOCK`(409).
- **모바일**: 장바구니 탭 신설(4탭 구성), `QuantityStepper` 컴포넌트 추가, 상품 상세에 수량 선택 + 담기 연동(비로그인 시 로그인 화면으로 유도). TanStack Query 뮤테이션은 응답으로 받은 장바구니 전체를 캐시에 덮어써 재조회를 없앴고, 캐시 키에 accountId를 넣어 계정 전환 시 이전 장바구니가 잠깐 보이는 문제를 막음.
- **[구조적 버그] 소프트 삭제 vs UNIQUE 제약**: 장바구니에서 상품을 뺐다가 다시 담으면 500이 나는 걸 발견 — 소프트 삭제(`del_yn='Y'`)된 행이 UNIQUE 슬롯을 계속 점유하는 게 원인. 장바구니만의 문제가 아니라 **같은 유형의 제약 17건 전부가 동일한 잠재 버그**여서 한꺼번에 부분 유니크 인덱스(`WHERE del_yn='N'`)로 교체(Flyway `V3`). 반대로 "한 번 쓰인 값은 영구 점유"가 맞는 것들(주문번호, 쿠폰 계정당 1회, 약관 동의, 정산 등)은 의도적으로 엄격하게 유지. 자세한 목록/판단 근거는 `ERD.md` "14차 라운드" 참고.
  - **검증**: 마이그레이션 경로(V1+V3)와 신규 설치 경로(`schema.sql`)가 어긋나면 나중에 크게 터지므로, 빈 DB에 `schema.sql`을 통째로 적용해 운영 DB와 UNIQUE 인덱스 목록을 비교 — Flyway 자체 테이블 빼고 완전 동일 확인.

### 주문/결제 + 관리자 콘솔
- **주문/결제(백엔드)**: `V4`로 주문/결제/배송/재고 공통코드 + 주문번호 채번 시퀀스 + 테스트 회사 배송비 정책 시드. `POST /api/orders`가 한 트랜잭션에서 주문 확정 전체를 처리 — 주문항목에 상품명/가격 스냅샷, 재고 차감 + `stock_histories` 기록, **회사별 배송 건 생성**(1주문:N배송)과 그 시점 정책 기준 배송비 스냅샷, 결제 기록, 장바구니 비우기. 결제는 PG 연동이 없어 즉시 '완료'로 기록(개발 단계 한정). 주문 조회는 내부 PK가 아니라 `order_number`로 노출하고, 상세는 소유자 확인을 해서 주문번호만 알면 남의 주문을 볼 수 없게 막음.
- **주문/결제(앱)**: 주문서(배송지 입력) → 주문 완료 → 주문 내역 화면. 배송비 로직은 실제로 3만원 미만 주문(3,000원)과 이상 주문(무료) 둘 다 태워서 확인.
- **관리자 콘솔(Next.js `frontend/`)**: 관리자는 표·일괄작업 위주의 데스크탑 작업이라 앱이 아니라 웹에 만들었다. 로그인 / 대시보드(주문수·순매출·상품수·회원수·재고부족) / 주문 관리(상태 변경) / 상품 관리(가격·재고·상태 인라인 수정). 모바일과 같은 테크팩 토큰을 Tailwind v4 `@theme`로 옮겨 디자인을 통일.
- **권한 체계 정리**: JWT에 `common_codes.id`(예: `CCOD000...1`)를 role로 넣고 있어서 권한 검사에 쓸 수 없는 상태였다 → `ADMIN`/`GENERAL` 같은 의미 있는 값으로 바꾸고, `SecurityConfig`에서 `/api/admin/**`를 `hasRole("ADMIN")`으로 제한. 일반회원 토큰으로 관리자 API 호출 시 403 되는 것 확인.
- **관리자 재고 수정도 감사 이력을 남긴다**: 주문 차감과 동일하게 `stock_histories`에 '재고조정'으로 기록(누가 언제 얼마나 바꿨는지).
- **트러블슈팅**: Next.js 16은 `AGENTS.md`가 "학습 데이터와 다르니 번들된 docs를 먼저 읽으라"고 명시해서 `node_modules/next/dist/docs/`를 읽고 작업(App Router + Turbopack 기본 + async request API). 관리자 세션을 effect에서 `setState`로 읽었다가 lint 규칙(`set-state-in-effect`)에 걸려 `useSyncExternalStore`로 교체했는데, 이때 서버 스냅샷을 `null`로 두니 **하이드레이션 직후 "로그아웃"으로 오판해 로그인 화면으로 튕기는 버그**가 생김 → "아직 모름" 센티널을 따로 둬서 해결.
